## Application Context

Many systems require to perform operations on entities where order matters. Consider transactions keyed by an account, an order, or a customer, the use case chosen for this project. Operations on the same entity must apply in the order they arrived, because a later update depends on an earlier creation. Apply event queue can ensure that all operation are processed in order. However executing all operations across diferent record in a single event stram is every slow. A distributed event queue resolves this tension by partitioning on the ordering key, which preserves order within each entity while different entities proceed concurrently. Acknowledgment gates reserve the unit of work for each event transaction. Hence, keeps failures recoverable, since Nowacki et al. (2021) withhold removal of a message until its processing is confirmed, which allows an unacknowledged event to be retried at the head of its queue. Idempotent consumers, dead letter queues, and event replay reinforce that recoverability (Ratra et al., 2025).

The proposed prototype is a light-weight event broker that processes keyed events in real time, functioning as the streaming event counterpart that operates within a single process. Events carry an ordering key which dictate that events share a key are handled in strict first in, first out order, whereas events with different keys proceed concurrently. A consumer receives an event, records it, waits for a simulated duration of work, and then acknowledges completion, and that acknowledgment releases the next event in the same key group. This behavior explains why the application depends so heavily on its underlying data structures, because ordering, concurrency, and flow control all follow from how events are stored and retrieved rather than from features layered on top. Ratra et al. (2025) situate this class of system within high throughput architectures driven by events, which they present as the foundation for responsive fulfillment platforms that must absorb unpredictable traffic while preserving low latency, and they identify strict first in, first out ordering and duplicate handling as requirements for reliable state transitions. Nowacki et al. (2021) reinforce the framing through a dedicated event queue management system whose purpose is to store events safely and advance them under controlled conditions. Two structures carry the design. A hash map associates every ordering key with its own queue, and a first in, first out queue holds the pending events for a single key. The sections that follow justify each choice on grounds of time complexity, space efficiency, and ease of implementation.

## Data Structure Design

The design pairs a hash map for routing with a queue for ordering, and each subsection examines one structure together with the research that supports it.

### Hash Map for Key Partitioning

A hash map, implemented as the native Map type in the runtime, associates each ordering key with the queue that holds that key's events. Lookup, insertion, and deletion operate in constant time on average, which allows the engine to route an arriving event to its lane without scanning existing keys. This routing model mirrors key grouping in stream processing, where, as Liu et al. (2024) explain, tuples that share a key are directed to the single instance responsible for that key through a hash function. The same principle lets the engine advance many keys at once while keeping every individual key on one queue, so ordering within a key is never at risk. Assigning a key to exactly one lane also reflects a deliberate compromise. Splitting a single busy key across several workers can balance load, yet it undermines the ordering guarantee and introduces cost, as Liu et al. (2024) observed:

> Key-Splitting is an effective technique that distributes tasks associated with keys to downstream operators, facilitating load balancing at a relatively low cost. However, overly increasing parallel instances can lead to excessive aggregation costs, becoming a system bottleneck. (p. 164)

The design therefore keeps each key intact and gains concurrency across keys instead. Uneven key popularity remains a recognized risk, because skewed distributions can concentrate load on a small number of lanes and create hot spots that behave as bottlenecks (Ratra et al., 2025). The single process prototype treats that concern as a scaling topic for later phases rather than a correctness problem.

### Custom FIFO Queue and Ordering Gated by Acknowledgment

Each lane uses a queue built as a linked list with explicit head and tail references, which keeps enqueue and dequeue at constant time. This choice avoids the linear cost of removing an element from the front of a dynamic array, an operation that must shift every remaining element and therefore scales poorly as a lane grows. The queue enforces order within a key, and acknowledgment controls when the next event may advance. When a consumer finishes an event it calls acknowledge, which removes the completed event and dispatches the new head, so exactly one event per key is ever in flight. Nowacki et al. (2021) describe an equivalent discipline in their sequential queue, which advances to the next message only after the previous one succeeds, and their Acknowledgment Manager withholds removal of a message until a worker confirms the outcome. This gate is also a flow control device. Hanif et al. (2020) define backpressure as the condition in which a pipeline produces data faster than downstream operators can consume it, and they note that the pressure propagates in the opposite direction toward the source. Holding the next event until the current one is acknowledged matches producer speed to consumer speed within each lane, which supplies the same rate matching effect at the level of a single key. Ratra et al. (2025) similarly pair strict First In First Out queues with idempotent consumers as a pattern for dependable state transitions, which reinforces the combination of ordering and acknowledgment adopted here.

## Complexity and Space Efficiency

The two structures give the engine predictable cost. Key lookup, insertion, and deletion in the hash map run in constant time on average, and every queue operation, namely enqueue, dispatch, and dequeue, also runs in constant time because the linked list touches only the head or the tail. No operation on the normal path depends on the number of keys or the number of buffered events, which keeps dispatch latency stable as the workload grows. Space consumption scales with the number of active keys plus the number of events currently buffered across all lanes, and a lane that fully drains can release its map entry so that memory tracks active keys rather than every key ever seen. Formal analyses of partitioning support this attention to both dimensions. Liu et al. (2024) report linear bounds for tuple collection and assignment together with explicit memory bounds for their routing structures, which demonstrates that a partitioning layer can be reasoned about in terms of time and space at the same time. Ease of implementation is a further advantage. The hash map is provided natively by the runtime, and the queue is a small linked list with two pointers, so the design needs no external dependency and stays straightforward to document and test. The queue also serves as the surface where flow control takes effect, since a bounded lane is the point at which backpressure becomes observable, consistent with the queue based view of backpressure described by Hanif et al. (2020).

## Implementation Framing

The design maps onto a small set of modular and documented components. An Event holds its key, identifier, payload, and a reference to its queue, and it exposes a single acknowledge method. A Queue manages one lane. An Event Queue Manager owns the hash map, the shared event emitter, and a counter of pending events, and it creates or locates the correct lane for each arriving key. A Consumer listens for dispatched events, records them, waits for the simulated work, and acknowledges, while a Producer supplies the input events. Completion is reached only when the pending counter returns to zero after the producer has finished, a guard that prevents a premature end when a lane empties before every event has arrived. The prototype is written in JavaScript on Node.js rather than Python, a deviation that the instructor approved and that this report records for transparency, and it is packaged with a container definition so the demonstration runs reproducibly. The engine delivers concurrency on one event loop rather than true parallelism, so many lanes interleave without running on separate processors. Broader scaling remains future work. Nowacki et al. (2021) present a distributed queue system with an Acknowledgment Manager across independent modules, and Ratra et al. (2025) survey partitioning, replication, and dead letter queues for high throughput deployments, and together these sources outline the path from this single process prototype toward a distributed successor in a later phase.
