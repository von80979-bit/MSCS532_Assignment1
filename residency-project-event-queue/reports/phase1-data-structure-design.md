# Data Structure Design and Implementation for a Keyed Event Queue Engine

## Application Context

Many systems process operations whose outcomes depend on one another, and those dependencies dictate the order in which the resulting transactions must be applied. In an e-commerce order, for example, an order shipped transaction is causally dependent on an earlier inventory reserved transaction, so the two must run in that order, whereas independent transactions, such as those belonging to a different order, carry no such constraint and may proceed concurrently. Two approaches enforce this ordering but scale poorly. Processing every transaction in one sequential order preserves the order, yet latency grows as volume increases. Alternatively, the caller can orchestrate the transactions across the respective consumers, but this tightly couples the services and complicates their management. A distributed event queue resolves this tension by partitioning events on an ordering key, which preserves the order within each group of dependent transactions while independent transactions proceed concurrently. Acknowledgment lets the queue reserve each unit of work and withhold the next transaction until the current one is confirmed, a discipline that also keeps failures recoverable. As Nowacki et al. (2021) describe, the system withholds removal of a message until its processing is confirmed, so an unacknowledged transaction can be retried at the head of its queue without advancing past it. Idempotent consumers, dead letter queues, and event replay reinforce that recoverability (Ratra et al., 2025).

The proposed event queue is a lightweight, in memory event broker that processes events in real time and reproduces the ordering and concurrency of a full event broker within a single process. It serves as a proof of concept and a foundation for understanding event brokers at larger scale, where the data structures and components used here could form the basis of a full service. Each event carries an ordering key, which dictates that events sharing a key are handled in strict first in, first out order, whereas events with different keys proceed concurrently. A consumer receives an event, records it, waits for a simulated duration of work, and then acknowledges completion, and that acknowledgment releases the next event in the same key group. This behavior explains why the application depends so heavily on its underlying data structures, because ordering, concurrency, and flow control all follow from how events are stored and retrieved rather than from features layered on top. Ratra et al. (2025) situate this class of system within high throughput, event driven architectures that support responsive fulfillment platforms, and they identify strict first in, first out ordering and duplicate handling as requirements for reliable state transitions. Nowacki et al. (2021) reinforce the framing through a dedicated event queue management system whose purpose is to store events safely and advance them under controlled conditions. Two structures carry the design: a hash map associates every ordering key with its own queue, and a queue holds the pending events for a single key. The sections that follow justify each choice on grounds of time complexity, space efficiency, and ease of implementation.

## Data Structure Design

The design pairs a hash map for routing with a queue for ordering, and each subsection examines one structure together with the research that supports it.

### Hash Map for Key Partitioning

A hash map, implemented using the native Map data structure in NodeJs, associates each ordering key with the queue that holds the events carrying that key. Lookup, insertion, and deletion operate in constant time on average, which allows the engine to route an arriving event to its queue without scanning existing keys. This routing model mirrors key grouping in stream processing, where, as Liu et al. (2024) explain, tuples that share a key are directed to the single instance responsible for that key through a hash function. The same principle lets the engine advance many keys at once while keeping every individual key on one queue, so ordering within a key is never at risk. Assigning a key to exactly one queue also reflects a deliberate compromise. Splitting a single hot key partition across several workers can balance load between instances, but it would break the ordering guarantee that keeping a key on one queue provides. Liu et al. (2024) further note that key splitting distributes a key's tasks across downstream operators and balances load at a relatively low cost, yet raising the number of parallel instances too far drives up aggregation costs until they become a system bottleneck. The design therefore keeps each key intact and gains concurrency across keys instead. Uneven key popularity remains a recognized risk, because skewed distributions can concentrate load on a small number of queues and create hot spots that behave as bottlenecks (Ratra et al., 2025). The single process prototype treats that concern as a scaling topic for later phases rather than a correctness problem.

### Custom FIFO Queue and Ordering Gated by Acknowledgment

Each queue is built as a linked list with explicit head and tail references, which keeps enqueue and dequeue at constant time. This choice avoids the linear cost of removing an element from the front of a dynamic array, an operation that must shift every remaining element and therefore scales poorly as a queue grows. The queue enforces order within a key, and acknowledgment controls when the next event may advance. When a consumer finishes an event it calls acknowledge, which removes the completed event and dispatches the new head, so exactly one event per key is ever in flight. Nowacki et al. (2021) describe an equivalent discipline in their sequential queue, which advances to the next message only after the previous one succeeds, and their Acknowledgment Manager withholds removal of a message until a worker confirms the outcome. This gate is also a flow control device. Hanif et al. (2020) define backpressure as the condition in which a pipeline produces data faster than downstream operators can consume it, and they note that the pressure propagates in the opposite direction toward the source. Holding the next event until the current one is acknowledged matches producer speed to consumer speed within each queue, which supplies the same rate matching effect at the level of a single key. Ratra et al. (2025) similarly pair strict first in, first out queues with idempotent consumers as a pattern for dependable state transitions, which reinforces the combination of ordering and acknowledgment adopted here.

## Complexity and Space Efficiency

The two structures give the engine predictable cost. Key lookup, insertion, and deletion in the hash map run in constant time on average, and every queue operation, namely enqueue, dispatch, and dequeue, also runs in constant time because the linked list touches only the head or the tail. No operation on the normal path depends on the number of keys or the number of buffered events, which keeps dispatch latency stable as the workload grows. Space consumption scales with the number of active keys plus the number of events currently buffered across all queues, and a queue that fully drains can release its map entry so that memory tracks active keys rather than every key ever seen. Formal analyses of partitioning support this attention to both dimensions. Liu et al. (2024) report linear bounds for tuple collection and assignment together with explicit memory bounds for their routing structures, which demonstrates that a partitioning layer can be characterized in terms of both time and space. Ease of implementation is a further advantage. The hash map is provided natively by the NodeJs runtime, and the queue is a small linked list with two pointers, so the design needs no external dependency and stays straightforward to document and test. The queue also serves as the surface where flow control takes effect, since a bounded queue is the point at which backpressure becomes observable, consistent with the queue based view of backpressure described by Hanif et al. (2020).

## Implementation Framing

The design maps onto a small set of modular and documented components. An Event holds its key, identifier, payload, and a reference to its queue, and it exposes a single acknowledge method. A Queue manages the events for a single key. An Event Queue Manager owns the hash map, the shared event emitter, and a counter of pending events, and it creates or locates the correct queue for each arriving key. A Consumer listens for dispatched events, records them, waits for the simulated work, and acknowledges, while a Producer supplies the input events. Completion is reached only when the pending counter returns to zero after the producer has finished, a guard that prevents a premature end when a queue empties before every event has arrived. The prototype is written in JavaScript on Node.js and packaged with a Docker container definition so the demonstration runs reproducibly. It delivers concurrency rather than true parallelism, because it runs on a single event loop rather than on separate processors. Broader scaling remains future work. Nowacki et al. (2021) present a distributed queue system with an Acknowledgment Manager across independent modules, and Ratra et al. (2025) survey partitioning, idempotent consumers, and dead letter queues for high throughput deployments, and together these sources outline the path from this single process prototype toward a distributed successor in a later phase.
